01
Proposed approach

What should we buy or adopt natively?

Current position
Start with the client’s existing identity, document storage, meeting capture, task tracking and managed model services. Compare native automation/reporting with the required workflow before building replacements.
Prototype boundary
The prototype demonstrates the workflow with a custom local UI and API calls. It does not establish that custom infrastructure is cheaper or better than the tenant’s native tools.
Still to discuss
What is already licensed and approved? Which native capabilities satisfy quality, permissions, export and integration needs? What are their operating and migration costs?
Evidence / next step
Inventory the tenant’s tools, trial one native alternative on the same source pack and compare total effort, capabilities and cost.

02
Proposed approach

What should we build for this business?

Current position
Own the MEP-specific KPI definitions, source-to-field mappings, report contract, audience rules and representative evaluation cases. Build UI or orchestration only where it materially improves the workflow.
Prototype boundary
Metric calculations, evidence checks, report assembly and exports are implemented. General-purpose source adapters, tenant integrations and permissions are not.
Still to discuss
What is actually distinctive? What changes frequently? Who maintains each custom component? Does it justify the cost compared with extending a native tool?
Evidence / next step
Map each requirement to an existing capability or a justified custom component; assign an owner and maintenance budget.

03
Partly implemented

What should stay provider/model agnostic?

Current position
Keep provider calls and source connectors behind separate interfaces, with a shared report structure and a provider-independent evaluation set.
Prototype boundary
Four provider adapters share drafting instructions and an output schema. API details, model settings, pricing and behaviour remain provider-specific. Future connector portability is a design proposal.
Still to discuss
Which proprietary features are worth the dependency? Can an alternative meet quality and confidentiality requirements? How will prompt changes, version changes and migrations be tested?
Evidence / next step
Run contract checks and held-out evaluations before switching. Version prompts/models and keep a rollback option; reassess processing terms and residency for each deployment.

04
Assumption to validate

Are we saving work or just moving it?

Current position
Use a reliable platform export; adapt known formats automatically; use assisted intake for unfamiliar formats; route unresolved exceptions to source/platform owners.
Prototype boundary
The prototype validates an agreed format. Some normalisation is implemented, but arbitrary spreadsheet repair, assisted intake and automatic exception routing are not. The eight-to-two-hour saving is a hypothesis.
Still to discuss
How much time goes into finding files, preparing them, correcting errors and reviewing the report? Is that work shifted to another team? Who fixes a changed export?
Evidence / next step
Time comparable reports before and after the pilot. Include preparation, exceptions and corrections; track first-pass success and source-team effort. Do not substitute model latency for business time saved.

05
Deployment gate · open

Can confidential material be processed and retained safely?

Current position
Assess permission to process each data class, minimise what is sent and retained, and use an approved provider deployment with appropriate access, retention and deletion controls.
Prototype boundary
Extracted notes go to the configured provider. Local draft JSON retains source text. Application-level encryption, multiuser permissions and retention/deletion are not implemented. A local .env or a no-storage API flag is not a complete confidentiality solution.
Still to discuss
What documents may leave the tenant? Which regions, contracts, logging and retention settings are approved? Who can access saved sources? When are records, caches and backups deleted?
Evidence / next step
Complete a security/data-owner review of the actual account and deployment. Test access isolation, deletion and incident handling with synthetic data before confidential use.

06
Conditional recommendation

When should we change the model or provider?

Current position
Use measured output quality, reliability, latency and total cost for this task. Change models when representative evidence shows a gap that a different model can address.
Prototype boundary
Haiku is the configured drafting default; the separate assisted-intake evaluation conditionally favours Gemini. Assisted intake is not wired into production. Synthetic results do not guarantee completeness or authorise confidential processing.
Still to discuss
What error/omission rates and latency are acceptable? Do larger or messier inputs change the result? Can a stronger model improve failures enough to justify cost and confidentiality changes?
Evidence / next step
Agree acceptance thresholds, use independently reviewed held-out cases, track omissions and corrections, and re-evaluate on model/prompt changes. Compare against the non-AI baseline where useful.

07
Production design · open

What breaks as usage grows?

Current position
Distinguish more requests from harder requests. More users first require concurrency control, queues, rate-limit handling, storage and operational monitoring; they do not automatically require a heavier model.
Prototype boundary
This is a local app with bounded inputs, synchronous API calls, no automatic retries and local JSON history. It is not a shared production service.
Still to discuss
How many reports and concurrent users? How large are the files? What is the cost including retries, extraction, storage and review? What happens on duplicate requests, timeouts or provider outages?
Evidence / next step
Load-test a representative workload; define latency/cost budgets and failure behaviour. Design bounded retries, idempotency, managed storage and observability before expanding.

08
Boundary established · extensions open

What stays with people, and when should actions be automated?

Current position
BD selects the intended audience and uploads evidence, then downloads and reviews the output. People retain responsibility for meaning, commitments and external disclosure. Use agents only where autonomy has a demonstrated benefit.
Prototype boundary
There is no approval form and downloading does not attest review. Checks verify quotation matching, not factual truth or completeness. The prototype does not send reports or write Jira tasks.
Still to discuss
What level of review is required by the organisation? Which future writes need explicit authorisation? Who owns engineering priorities and prevents duplicate or inappropriate tasks?
Evidence / next step
Keep draft generation separate from action execution. Start with one reviewed destination, scoped API access, duplicate protection and clear ownership.

09
Assumptions to validate

Where does the evidence come from, and how fresh is it?

Current position
Separate meeting evidence from operational telemetry. Govern metric definitions, source ownership, freshness and missing updates. Begin future intake with one approved document source.
Prototype boundary
Uploads feed the report. The Overview dashboard is fictional mock data and does not update from uploads. Connectors, retrieval and automatic quarterly consolidation are not implemented.
Still to discuss
Which source owns WAU, availability and delivery status? What happens if a meeting is missed or unrecorded? How do we detect changed files, permission changes, duplicates and missed events?
Evidence / next step
Agree definitions and refresh expectations. For connectors, validate webhook/delta/polling support and use reconciliation, version tracking and permission-aware retrieval. Collection cannot invent undocumented decisions.

10
Current decision: keep selection explicit

Can the system infer the right report from the files?

Current position
Keep Engineering, Vendor or Partner as an explicit choice because the same evidence can support different meetings. A report-type prompt changes focus; it is not a disclosure-control mechanism.
Prototype boundary
All selected source material is sent to the model. The prototype does not implement recipient-specific source filtering, partner isolation or automatic confidentiality clearance.
Still to discuss
Can internal engineering material appear in a Swisscom briefing? Should the system suggest an audience, require a named recipient, or withhold restricted sources? How do app-provider and vendor roles affect access?
Evidence / next step
Define recipient/source permissions and test mixed-audience cases. Treat automatic audience selection as a later evaluated feature, with clear handling of ambiguity.
